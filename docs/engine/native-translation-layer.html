AE1 Translation Layer

The canonical map from AE1 engine terminology, libraries, methods and strategies to how each is manifested in the two build targets — the browser build and the Windows desktop build. Its purpose: to rapidly diagnose destabilised or incompatible regions of the pipeline, and to know exactly which layer a symptom belongs to.

Doctrine. The AE1 engine is one codebase — never forked. Portability lives entirely in four seams: gfx (renderer), platform (window/input/time), input3d & env3d (engine-facing bridges). The browser and native targets are two implementations behind those seams; the game logic, scene, scheduler and the guarded motion-matching core run identically on both.

01The manifested target

Both targets consume the same AGP (AE1 Game Package): a target-neutral container of manifest.json + data.json + game.aepack. They differ only in the shell wrapped around it.

The native runtime is a Build & Ship target only. The editor, tools and the motion-matching lab stay in the browser forever. The .mmcache/ is generated on first launch (or pre-warmed by the exporter) and holds the motion-matching gait tables so later launches skip the ~6 s build.
